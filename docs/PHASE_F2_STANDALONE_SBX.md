# Phase F2 standalone sbx runner

MPX accepts only the standalone Windows `sbx.exe` v0.39.0 build `def8cb0523a77e757bdd6ef52b459fe374f3783e`, SHA-256 `b064711a10f22363953e90eae926dbd9d96419e601f9308cd9d1102e3d81ccbf`. The legacy Docker CLI sandbox plugin is never discovered or invoked.

## Read-only discovery

`mpx doctor` and Docker launch use an absolute `MPX_SBX_EXECUTABLE`, or absolute PATH entries, and verify the binary hash and real path outside the project. They invoke only `version`, `--help`, `daemon status --json`, `diagnose --output json`, and the read-only global-policy preflight `policy ls --json`, with `shell:false`, bounded output and a minimal OS-path child environment (no tokens or credentials). A failing policy preflight is typed `SBX_GLOBAL_POLICY_UNINITIALIZED`. Unknown JSON/help fields and version/build drift fail closed. Discovery never runs daemon start/restart/reset, login, create, or attach.

Plans use v0.39 argv only: `create --name`, `run --name`, `exec`, `ports`, sandbox-scoped `policy allow network --sandbox`, read-only `policy check network --sandbox ... --json`, `policy ls --json`, `ls --json`, and `rm --force`. `policy add`, `policy set`, and local `--profile` creation do not exist. One proof-bound `StandaloneSbxLifecycleAdapter` executes the reviewed create/port/policy lifecycle and marks cleanup required only after `create` succeeds, so a rejected or nonzero create cannot manufacture a false teardown failure. Cleanup is idempotent; a cleanup failure is reported without replacing the primary lifecycle error. `StandaloneSbxExecutorAdapter` is its executor-facing API rather than a duplicate implementation. For Pi it starts the launch-private worker before attach and exposes only its bridge endpoint/attestation to runtime planning. For built-in Claude it delivers the immutable projection and launches the VM agent. The production CLI factory in `apps/cli/src/sbx-execution.ts` needs no caller injection. Exact proof `reportKey` evidence is reported only when pinned diagnostics pass and a strict live `F2ProofReportV2` exactly matches the configured canonical `SbxLaunchPlanExportV1`, regenerated plan, packaged inventory, pin, and executor evidence; otherwise Docker remains gated. V1 is accepted only by explicitly injected offline/fixture test boundaries and is never production admission evidence. Clone mode is main-checkout-only; host-worktree mode is linked-worktree-only. The workspace itself and extra mounts are checked against host runtime roots, credentials, the opposite identity domain, Docker sockets, and the Git common directory. A reviewed direct-main checkout may contain its own `.git`, but that does not permit a Git common directory above or outside the workspace. Environment is generated identity-local state only; host `CLAUDE_CONFIG_DIR`, native account paths, credentials, and the host Docker gateway are never forwarded.

## Production built-in Claude route

Claude launches use the built-in `claude` agent from the pinned standalone sbx release, never a host Claude executable. Every lifecycle command is scoped to `--app-name mpx-claude-personal` or `--app-name mpx-claude-work`. The proof contract carries a closed `builtInClaudeEvidence` record with independently captured enrollment, credential-isolation, opposite-identity-denial, and capture-signature digests for **both** app identities. A new Claude VM is denied before `create` unless the adapter receives the exact same live evidence record; offline reports carry `null` and remain denied. Signed fixture evidence is accepted only where tests pass it explicitly and is report-key bound; MPX no longer manufactures a credential attestation from projection or report hashes. MPX sends a digest-verified projection archive over stdin to `mpx-projection-receiver` and installs it at `/opt/mpx/projections/<sha256>`. It is not mounted from a native root or mutable host skill store.

The built-in Claude argv references only that VM projection's plugin and aggregate MCP configuration. The aggregate configuration targets the launch-bound Docker worker/policy surface, whose exact MCP, web/content, and development-service tool inventory is attested. `apps/cli`'s Claude gateway remains a host-executor adapter and is never projected, mounted, or named by this route. Host projection paths, native account roots, `CLAUDE_CONFIG_DIR`, API keys, and credential environment are rejected or omitted.

MPX logical policy names are `open`, `deny-all`, `minimal`, `implementation`, `delivery`, and `research`; they remain in `sandbox.profile` but are never passed as sbx `--profile`. The selected standalone baseline is `open`, mapped to the sbx global `allow-all` policy. It has default allow, no destination isolation, no sandbox-scoped allow/deny mutation, one canonical bounded allow evaluator probe, and no claimed deny evidence. Deny-default profiles remain available: MPX materializes their sorted allow targets after create and requires the fixed deny sentinel as evidence of the global deny default. Acceptance requires exact read-only policy-check decisions and never relies on policy logs. Since v0.39.0 has no no-shared-skills flag, effective mount-table inspection and rejection of `.claude`, `.pi`, or skills mounts remain required live observations; the V2 runner does not perform them.

## Fake proof

The production fake supports the complete pinned diagnostic and lifecycle surface (`version`, help, daemon diagnostics, create, attach, exec, policy, ports, list, and delete), including identity-scoped `--app-name` calls. The fake-sbx CLI launch test exercises built-in Claude, stdin projection delivery, content-addressed VM argv, Docker-worker MCP/dev calls, secret-free environment/argv, exact signed-fixture evidence mismatch, and awaited delete without a daemon, container, or authentication. Offline fake proof emits only V1 fixture hashes; the live production runner emits a strict export-bound V2 report. Raw stdout, stderr, paths, prompts, credentials, and fake secrets are not retained. Stored proof is invalid when the runtime-tool inventory digest changes.

## Export-first live opt-in (gate remains incomplete)

1. A human selects the project, runtime, identity, workspace mode, and named network policy, then exports the reviewed Docker plan with `mpx --json --cwd <project> launch sbx-plan-export --runtime <claude|pi> --identity <name> ...`.
2. Review the closed `SbxLaunchPlanExportV1`: launch/descriptor/artifact binding, packaged pin/inventory/executor digests, production create argv, deterministic proof name, policy default, and evaluator targets for exactly the profile selected at sandbox creation. Deny-default profiles require sorted allows plus `blocked.invalid:443`; `open` requires canonical allow probe(s) and forbids deny claims. A different profile requires a separate launch-bound export and proof.
3. Review the machine-wide consequence, then perform the one-time human initialization `sbx policy init allow-all` before MPX create. **This global allow-all affects every sbx sandbox on the machine and provides no destination-egress isolation.** MPX never initializes or changes the global default. Start/authenticate the daemon manually and set `MPX_SBX_EXECUTABLE` to the absolute pinned binary; MPX never starts, resets, logs in, or authenticates it.
4. Run `scripts/run-f2-live-proof.ps1 -PlanFile <export.json> -PlanExportKey <reviewed-key> -ConfirmLive -ConfirmPhrase 'RUN MPX F2 LIVE PROOF'`.
5. Before confirmation the runner resolves packaged evidence from its own repository root, validates the bounded raw export and canonical key, and makes no `sbx` call. A plan key alone fails with `PLAN_EXPORT_REQUIRED`.
6. After confirmation it first performs read-only `policy ls --json`, creates only from the reviewed profile-free argv (substituting only the reviewed deterministic proof name), materializes exact exported allows only for deny-default profiles, and runs `policy check network --sandbox <proof-name> <target> --json` once per exported target. For `open`, it performs only canonical bounded safe allow probe(s), adds no sandbox-scoped network rule, and claims no deny evidence. It cleans up after successful creation and emits `F2ProofReportV2` containing only evaluator decisions/counts and bound evidence. Policy checks do not generate traffic, so `policy log` is not target proof and is not part of V2 admission.

The runner verifies pinned executable/evidence, successful policy preflight and create, evaluator allow decisions, and successful `rm` before report emission. It does not inspect the effective mount table, version result, port publication, real traffic, host-Pi bridge/OAuth, or post-cleanup zero-sandbox inventory. A narrow personal-Pi/open invocation may have occurred, but no retained tracked launch-bound V2 plan/report exists to close repository-verifiable acceptance.

Production admission and `mpx doctor` require absolute `MPX_F2_PROOF_REPORT_FILE` and `MPX_F2_PLAN_EXPORT_FILE` bindings with an exact V2 report/export match; V1 reports remain offline fixtures only. This workflow documents required human inputs but does **not** mark the live F2 gate complete.
